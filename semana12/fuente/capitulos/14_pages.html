14.1 Prompt original

P12 Prompt original · chat 03:01:41 (repetido 03:05:05) · ProfesorDestino: OpenCode · texto literal
Indicación oral: pegarlo «donde hicimos la landing page», en la misma conversación de DENTEA o de la landing personal. Puede pedir un nombre de repositorio: «ustedes le pueden inventar uno».

Lectura del prompt: «despliega en GitHub Pages la landing page ya pública» significa «publícala para que ya sea pública». Es breve porque se apoya en el contexto de la conversación (el agente sabe cuál es la landing). Su debilidad: no pide comprobar secretos, no dice qué hacer si hay que compilar, ni exige verificar que el enlace abre. La versión mejorada del subagente está en los Anexos B1/B2 (P12); abajo, un resumen de lo que debe hacer.

14.2 Diferencias fundamentales

Archivo localSolo está en tu computadora.
RepositorioAlmacena y versiona el código en GitHub.
GitHub PagesDocs «Servicio de alojamiento de sitios estáticos que toma HTML, CSS y JavaScript de un repositorio, opcionalmente los procesa con un build, y publica un sitio». En cuentas gratuitas, solo repositorios públicos.
App con backendSi necesita servidor, base de datos o claves API privadas, Pages no basta: requiere otro servicio (Firebase, Render, etc.). Nunca pongas claves API en el código de una página pública.
Dominio personalizadoDirección propia (tumarca.com) que compras y apuntas a Pages desde la configuración del repositorio.

14.3 Publicación paso a paso

  1. Comprueba que la app funciona en local.
  2. Identifica la carpeta correcta del proyecto (p. ej. dentea/).
  3. Revisa los archivos que se subirán.
  4. Comprueba que no hay secretos (.env, claves, contraseñas).
  5. Prepara .gitignore (node_modules/, .env, dist/ si usas Actions).
  6. Inicializa Git si no existe (git init).
  7. Crea el primer commit.
  8. Elige visibilidad: público para Pages gratis.
  9. Crea el repositorio remoto: gh repo create NOMBRE --public --source=. --push.
  10. Sube el proyecto (incluido en el paso anterior con --push).
  1. Configura Pages: Settings → Pages (o el agente vía gh api).
  2. Origen: rama (main, carpeta raíz) para HTML simple; GitHub Actions si hay que compilar (Vite: ajustar base: '/NOMBRE/').
  3. Espera el despliegue (de segundos a pocos minutos).
  4. Abre el enlace https://USUARIO.github.io/NOMBRE/.
  5. Verifica que coincide con la versión local.
  6. Prueba botones e interacciones.
  7. Comprueba que cargan imágenes y estilos (si falta el estilo, suele ser el base path).
  8. Ábrelo en tu celular.
  9. Identifica errores (404, página en blanco).
  10. Corrige, commit + push, y vuelve a verificar.
Prueba de verdadUna publicación está terminada cuando el enlace abre en otro dispositivo (tu celular con datos móviles, o alguien del grupo). Que el agente diga «listo» no basta.

14.5 Publicación en Firebase

Una estudiante publicó en Firebase Hosting (de Google), que también sirve sitios estáticos y ofrece funciones adicionales (bases de datos, autenticación). No es un fallo: es una alternativa válida, y el profesor la aceptó. La diferencia práctica es que la integración con los agentes vista en clase se configuró para GitHub.

14.6 Actualizaciones posteriores

Una vez conectado, en la misma conversación (o en una nueva dentro de la carpeta) puedes pedir: corregir una sección, añadir un botón, cambiar colores, ajustar el diseño móvil, solucionar un error, guardar cambios y actualizar la versión publicada. El profesor: «cuando hagas un cambio y le digas "quiero que ahora no se trate de dentista sino de otra cosa", ya lo va a poder hacer».
